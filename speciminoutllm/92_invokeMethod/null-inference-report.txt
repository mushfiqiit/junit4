

## A) Annotation decisions

| location | inferred annotation | one-sentence reason |
|---|---:|---|
| `FrameworkMethod.invokeExplosively` varargs parameter `params`, specifically the varargs **array type** | `@Nullable`, written as a type annotation on the array: `Object @Nullable ... params` | The caller may intentionally pass a `null` `Object[]` when the invoked method has zero parameters, so the varargs array itself must be allowed to be null. |
| `FrameworkMethod.invokeExplosively` parameter `target` | `@Nullable` | This call, and other JUnit call sites, pass `null` for the target object. |
| `BlockJUnit4ClassRunnerWithParameters.parameters` field | `@Nonnull` / leave unannotated | The field is assigned from `toArray(...)` and is itself not null; the nullable expression comes from the explicit `null` branch in the ternary, not from the field. |

No other annotations are required for this specific warning.

## B) Cause of the warning

The warning is triggered at:

```java
method.invokeExplosively(null, paramCount == 0 ? (Object[]) null : parameters);
```

The second argument is a ternary expression whose type is `Object[]`, and one branch is the `null` literal:

```java
paramCount == 0 ? (Object[]) null : parameters
```

Therefore NullAway infers the expression as `@Nullable`. The callee’s varargs parameter was treated as requiring a non-null array, so passing a potentially null array is unsafe.

For a varargs parameter, a simple `@Nullable` before the base type does not reliably annotate the **array itself** in a type-use/JSpecify-style interpretation; it may only affect the element type or parameter declaration. The fix is to annotate the varargs array type as nullable:

```java
Object @Nullable ... params
```

This tells NullAway that the array passed for `params` may be null, which matches the caller’s behavior when `paramCount == 0`.



## A) Annotation decisions

| location | inferred annotation | one-sentence reason |
|---|---|---|
| `org.junit.experimental.categories.Categories#createSet(Class<?>[] classes)` parameter `classes` | `@Nullable` | The original implementation explicitly checks `classes == null`, and callers can pass `null` when no category annotation is present. |
| `org.junit.experimental.categories.Categories.CategoryFilter#CategoryFilter(...)` parameters `inclusions` and `exclusions` | `@Nullable` already | These array references can be null when the corresponding annotation is absent, so passing them to `createSet` requires `createSet` to accept nullable input. |
| `org.junit.experimental.categories.Categories#createSet` return type `Set<Class<?>>` | non-null / leave unannotated | All original return paths return a non-null set, so assigning the result to the final fields `included` and `excluded` is safe. |

## B) Cause of the warning

The warning is reported at:

```java
excluded = createSet(exclusions);
```

because `exclusions` is declared as `@Nullable Class<?>[]` in the `CategoryFilter` constructor, while `createSet` declares its parameter `classes` with no nullability annotation, which NullAway treats as `@Nonnull`. Therefore, passing the possibly-null `exclusions` array to `createSet` is considered unsafe. The original JUnit code shows that `createSet` is intended to accept `null`, since it checks `classes == null` before using the array. Marking the `classes` parameter of `createSet` as `@Nullable` resolves the warning.
